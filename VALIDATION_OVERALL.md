# How this was validated

This sandbox has Node.js 22 but **no Dart/Flutter SDK**, and no network
access to install one (`storage.googleapis.com` / `dl.google.com`, where
the Flutter/Dart SDK is distributed, are outside the environment's
network allowlist). So the two halves of this project were validated
differently and to different degrees — this document says exactly what
was and wasn't run, rather than claiming uniform test coverage.

## Server (Node.js) — fully executed, 22/22 tests passing

Everything in `server/` was actually run in this environment:

- `npm test` runs `server/test/*.test.js` under Node's built-in test
  runner: **22 tests, 22 passing.**
- Fixture images (`server/test/fixtures/*.jpg/.png/.webp`) are **real
  files with real embedded EXIF/GPS**, generated by a Python script
  (`make_fixtures.py`) using Pillow + piexif — not hand-crafted byte
  arrays. The server's own hand-written TIFF/JPEG/PNG/WebP parser
  (`server/src/image/`) is checked against what an independent library
  (piexif) actually wrote, including:
  - GPS latitude/longitude/altitude round-tripping to ~6 decimal places
  - Capture date/time with timezone offset and sub-second precision
  - Camera Make/Model/lens/exposure/ISO
  - Orientation
  - DPI (XResolution/YResolution/ResolutionUnit)
  - JPEG **and** PNG **and** WebP (both lossy and lossless)
  - Negative cases: corrupt JPEG → `400`, non-image → `415`, a file
    claiming `image/jpeg` that isn't one → rejected by magic-byte
    sniffing, not by trusting the client
- The full Express app was booted for real (`npm start`), hit with
  `curl`, and its `db.json` / `assets/jpeg/...` output inspected by hand
  to confirm the end-to-end HTTP path works, not just the unit-level
  parser.

## Flutter app (Dart) — algorithms cross-validated, not compiled

The Dart code in `app/lib/services/metadata/` (the EXIF/TIFF writer, and
the JPEG/PNG/WebP embedders) could not be compiled or run directly, since
no `dart`/`flutter` binary is available here. To still get real evidence
rather than "it looks right," the **exact same byte-level algorithms**
were ported line-for-line to plain Node.js and executed against the
already-tested server-side parser:

- `TiffWriter`'s offset-planning (IFD0 → Exif sub-IFD → GPS sub-IFD,
  correctly placing values ≤4 bytes inline vs. spilling larger ones —
  ASCII strings, rationals — into the TIFF "overflow" value area) was
  ported and round-tripped: build → parse → assert GPS/camera/orientation/
  date/DPI all match, including a realistic mix of inline and overflow
  fields. **Passed.**
- `JpegContainer.embed` (strip any existing APP1 EXIF, insert a fresh one
  after SOI) was ported and checked to (a) produce a file the server
  parses with the new metadata, and (b) leave every byte from the SOS
  marker onward — the actual entropy-coded pixel data — byte-for-byte
  identical to the original. **Passed.**
- `PngContainer.embed` (drop any existing eXIf/pHYs, insert a new eXIf
  chunk after IHDR with a correct CRC-32) was ported and checked the same
  way, plus confirming every IDAT chunk (the actual pixel data) is
  untouched. **Passed.**
- `WebpContainer.embed` (upgrade a simple VP8/VP8L file to the Extended
  WebP format by adding a VP8X chunk and an EXIF chunk) was ported and
  checked against both a lossless and a lossy source file, confirming the
  image chunk type/bytes are preserved and the server correctly reads
  back the injected metadata. **Passed.**

That check script is not committed (it was a throwaway validation step,
deleted after use) — what's committed is the server-side test suite it
was validated against, which anyone can re-run.

**What this means concretely:** the arithmetic and container-format logic
that the Dart code implements is proven correct, because the identical
logic was executed and produced correct results. What is *not* verified
by this process is the Dart-to-Node *translation* itself — a typo in a
Dart-only detail (e.g. a `List<int>` vs `Uint8List` mismatch, an `Endian`
argument) wouldn't be caught this way. Before relying on this in
production, run:

```bash
cd app
flutter pub get
flutter test          # includes test/metadata_roundtrip_test.dart
flutter analyze
```

on a machine with the Flutter SDK installed, and fix anything the
analyzer flags. The `image` package's public API used here
(`encodeWebP(lossless:, quality:)`, `encodeJpg(quality:)`,
`encodePng()`, `bakeOrientation()`) and Dio's `MultipartFile.fromBytes`
contentType handling (`package:http_parser`'s `MediaType.parse`) were
each confirmed against their published API docs/source during
development (see the package versions pinned in `app/pubspec.yaml`), not
assumed from memory.

## What was not run at all

- No Android/iOS build, no emulator/device run of the Flutter app, no
  camera/location permission flow. `flutter create .` has not been run in
  this sandbox, so there is no `android/`/`ios/` platform folder yet —
  see the README's "First-time setup." Manifest/Info.plist permission
  entries to merge in after that step are provided as
  `app/android_permissions_snippet.xml` and `app/ios_permissions_snippet.plist`.
- No real device's camera EXIF was captured; the server-side validation
  used Pillow/piexif-authored files as the "known-good real EXIF"
  reference instead.
